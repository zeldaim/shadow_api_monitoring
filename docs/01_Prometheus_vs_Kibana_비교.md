# Prometheus vs Kibana(ELK) 비교 — Shadow API 탐지 관점

## 1. 한 줄 정의

| 도구 | 정의 |
|---|---|
| **Prometheus** | 시계열 **숫자(메트릭)** 수집·저장소. 대상의 `/metrics`를 주기적으로 긁어 간다(pull). 시각화는 보통 Grafana |
| **Kibana** | Elasticsearch에 저장된 데이터를 보는 **화면(UI)**. Kibana 자체는 수집·탐지를 하지 않는다 |
| **ELK 스택** | Filebeat(수집) → Elasticsearch(저장·검색) → Kibana(대시보드). "Kibana를 구축한다" = 이 세 개를 구축한다 |

> Wazuh 대시보드도 OpenSearch Dashboards(= Kibana 계열 포크) 기반이다. 즉 우리는 이미 Kibana류 화면 하나를 쓰고 있다.

## 2. 핵심 차이: 데이터를 "어디서, 어떻게" 가져오는가

```
                       ┌──────────────── WEB 서버 (192.168.20.10) ────────────────┐
[외부] → [방화벽] ──────→ │ 웹서버 ──→ 애플리케이션                                   │
  192.168.0.41:8080      │   │            │                                        │
                         │ access.log   /metrics (앱에 계측 코드를 넣어야 생김)      │
                         └───┼────────────┼────────────────────────────────────────┘
                             │            │
              Filebeat가 읽어 보냄(push)   Prometheus가 긁어 감(pull)
                             │            │  ※ prometheus.yml에 등록한 대상만
                             ▼            ▼
                    Elasticsearch      Prometheus
                             ▼            ▼
                          Kibana        Grafana
```

| 항목 | Prometheus | Kibana(ELK) |
|---|---|---|
| 수집 위치 | 앱 내부 계측 코드 또는 exporter가 노출한 `/metrics` | 서버에 쌓이는 **로그 파일** (웹서버 액세스 로그 등) |
| 수집 방식 | Pull — Prometheus가 대상에 접속 | Push — Filebeat가 로그를 읽어 전송 |
| 데이터 단위 | 집계된 숫자 (요청 수, 응답시간 분포) | 요청 **한 건 한 건**의 기록 (메서드, 경로, IP, 상태코드…) |
| 관측 범위 | **설정에 등록한 대상만** | 로그를 남기는 길목을 **지나간 모든 요청** |
| 경로(URL) 다루기 | 경로를 라벨로 넣으면 카디널리티 폭발 위험 → 사전 정규화 필수 | 원문 저장 후 수집 단계에서 정규화 필드 추가 가능 |
| 강점 | 서버·서비스 **상태 감시**, 알림, 가벼움 | **검색·포렌식**, 미지의 패턴 발견, 상세 드릴다운 |
| 약점 | "무엇이 호출됐나"의 원본이 없음 | Elasticsearch가 무겁다 (RAM 8GB+ 권장), 디스크 관리 필요 |

## 3. Shadow API 탐지에 왜 이 차이가 결정적인가

Shadow API = **조직이 모르는 API**.

- **Prometheus는 아는 것만 본다.**
  계측 코드를 넣고 scrape 대상으로 등록한 앱만 보인다. 누가 몰래 띄운 엔드포인트, 잊힌 레거시 앱, 디버그 포트는 `/metrics`도 없고 등록도 안 돼 있으니 **존재 자체가 안 보인다.**
  게다가 앱 프레임워크 계측은 "앱이 라우트로 인식한 경로"만 기록하는 경우가 많다.
- **로그는 지나가는 모든 것을 본다.**
  웹서버 액세스 로그에는 명세에 있든 없든 들어온 요청이 전부 남는다. 이것을 명세와 빼기 하면 Shadow API 후보가 된다.

```
Shadow  = 관측(로그) − 명세(OpenAPI)
Zombie  = 명세상 deprecated ∩ 관측(로그)
Phantom = 명세 − 관측   (명세에만 있고 실제 호출 없음 → 문서 품질 문제)
```

### 길목 로그의 한계와 보완

| 놓치는 것 | 보완 수단 | 우리 환경에서 |
|---|---|---|
| WEB 서버를 거치지 않는 요청 (다른 서버·포트로 직접 접속) | 방화벽 로그, 포트 스캔 | 방화벽 포트포워딩 목록 점검 |
| 트래픽이 아직 없는 열린 엔드포인트 (Dormant) | 자산 조회: 리스닝 포트 목록 | **Wazuh syscollector**가 에이전트의 리스닝 포트를 이미 수집함 → 활용 |
| 명세가 없는 서비스 | 명세부터 작성 | 확인 필요 |

→ 기존 ShadowAPI 프로젝트의 **명세 × 트래픽 × 자산 3원 대조**에 그대로 대응한다.
명세 = `api-inventory` 인덱스, 트래픽 = ELK 액세스 로그, 자산 = Wazuh syscollector.

## 4. 우리 토폴로지에 대입

| 위치 | IP | Prometheus를 쓴다면 | ELK를 쓴다면 |
|---|---|---|---|
| WEB (DMZ) | 192.168.20.10 | node_exporter + 앱 계측 → 알려진 API의 숫자만 | **Filebeat로 액세스 로그 수집 → 모든 요청** |
| DB (LAN) | 192.168.10.20 | DB exporter → DB 상태 | (선택) DB 로그 |
| Wazuh (LAN) | 192.168.10.30 | — | 자산 축(리스닝 포트) 제공 |
| 신규 수집 서버 (LAN) | 예: 192.168.10.40 | Prometheus + Grafana | **Elasticsearch + Kibana** |

방화벽 정책 관점에서도 ELK가 단순하다.
- ELK: **DMZ → LAN** 방향으로 `WEB → ELK:9200` 한 줄만 허용
- Prometheus: **LAN → DMZ** 방향으로 `Prometheus → WEB:9100(및 앱 포트)` 허용 (pull 방식이라 방향이 반대)

## 5. 세 번째 선택지: 기존 Wazuh 스택 재활용

Wazuh도 indexer(OpenSearch) + dashboard(Kibana 계열)를 가지고 있어 "Kibana 역할"을 맡길 수는 있다.

| | 별도 ELK 구축 (권장) | Wazuh 스택 재활용 |
|---|---|---|
| 자원 | VM 1대 추가 필요 | 추가 서버 없음 |
| 구성 자유도 | 정규화·명세 대조 파이프라인을 자유롭게 구성 | Wazuh가 관리하는 Filebeat 파이프라인·인덱스 템플릿과 섞임 |
| 데이터 분리 | 보안 경보와 API 트래픽 분리 | 모든 요청을 저장하려면 archives(logall) 활성화 → Wazuh 디스크 부담 급증 |
| 업그레이드 위험 | 독립적 | Wazuh 업그레이드 시 커스텀 설정 깨질 수 있음 |

→ **자원이 허락하면 별도 ELK**, VM 추가가 불가능하면 Wazuh 재활용을 검토한다.
어느 쪽이든 Wazuh는 **자산 축(리스닝 포트)**과 **알림 통로**로 계속 활용한다.

## 6. 그럼 Prometheus는 아예 필요 없나?

목표(Shadow API 탐지 + 대시보드)에는 **필요 없다.** 다만 아래가 새 요구사항으로 생기면 그때 추가를 검토한다.

- WEB/DB 서버의 CPU·메모리·디스크를 초 단위로 감시하고 임계치 알림 받기 (node_exporter)
- 서비스가 살아있는지 외부에서 주기적으로 확인 (blackbox_exporter)

이것도 ELK 쪽 **Metricbeat**로 대체할 수 있으므로, 당장은 스택을 하나로 유지하는 편이 운영 부담이 적다.

## 7. 최종 결정

| 항목 | 결정 |
|---|---|
| 수집·대시보드 | **ELK** (Filebeat → Elasticsearch → Kibana), 별도 VM, 비컨테이너 패키지 설치 |
| 수집 지점 | WEB 서버(192.168.20.10) 웹서버 액세스 로그 |
| 탐지 방식 | 수집 시 경로 정규화 → `api-inventory`(명세)와 자동 대조 → `documented / shadow / zombie` 태깅 |
| Prometheus | 보류 (서버 상태 감시 요구가 생기면 재검토) |
| Wazuh | 유지 — 자산 축(리스닝 포트), 알림 통로 |
